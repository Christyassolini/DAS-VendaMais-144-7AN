# ADR-001: Biblioteca de Conexão ao Banco de Dados — pyodbc vs SQLAlchemy

**Status:** Aceito | **Data:** 2026-05-28 | **Autores:** Design e Arquitetura de Software II

## Contexto

Esta decisão foi produzida como parte de uma atividade avaliativa da disciplina de Design e Arquitetura de Software II, cujo objetivo era comparar duas bibliotecas Python para acesso a banco de dados e determinar, a partir de uma Prova de Conceito (PoC), qual delas seria mais adequada para uso no projeto.

O projeto utiliza Azure Functions para executar pipelines ETL que realizam consultas a um banco de dados SQL Server (Azure SQL). Nesse cenário, surgiu a necessidade de escolher entre duas abordagens para a camada de acesso a dados:

- **pyodbc** — driver nativo de conexão ODBC, com acesso direto ao banco, sem camadas de abstração adicionais.
- **SQLAlchemy** — ORM (Object-Relational Mapper) que utiliza internamente o pyodbc como driver de conexão via `mssql+pyodbc`.

A PoC foi executada em Azure Functions (`azfun-vendamais-erp-025`), utilizando o mesmo banco de dados, a mesma tabela (`erp.cliente`) e a mesma query (`SELECT TOP 5 *`) para ambas as bibliotecas.

| Biblioteca   | Início da Conexão       | Fim da Conexão          | Tempo de Execução |
|--------------|-------------------------|-------------------------|-------------------|
| pyodbc       | 12:25:39.037538         | 12:25:39.057353         | ≈ 19,8 ms         |
| SQLAlchemy   | 00:09:31.997066         | 00:09:32.015725         | ≈ 18,7 ms         |

> Os tempos foram medidos a partir dos logs de início e fim de conexão registrados no Azure Portal.

## Decisão

Adotar o **pyodbc** como biblioteca de conexão ao banco de dados SQL Server.

Embora a diferença de performance entre as duas abordagens tenha sido mínima (≈ 1,1 ms), o pyodbc se mostrou mais adequado ao contexto do projeto por oferecer uma solução mais direta e enxuta para operações de consulta SQL simples, como as utilizadas em pipelines ETL. A conexão é estabelecida diretamente via string ODBC, sem a necessidade de criação de uma Engine intermediária.

## Consequências

(+) Código de conexão mais simples e fácil de manter.

(+) Menor número de dependências no `requirements.txt` (apenas `pyodbc`).

(+) Menor overhead de inicialização, sem necessidade de criação de Engine.

(+) Performance adequada para o volume e frequência das consultas atuais.

(-) Sem abstração ORM: consultas mais complexas exigem SQL manual.

(-) Migração para outro banco de dados pode exigir refatoração da string de conexão.

(-) Não aproveita recursos avançados do SQLAlchemy (sessions, lazy loading, migrations).

## Alternativas rejeitadas

- **SQLAlchemy**: apesar de oferecer abstração ORM completa e recursos avançados, adiciona dependências extras (`sqlalchemy` + `pyodbc`), maior overhead de inicialização via Engine e complexidade desnecessária para o caso de uso atual, que envolve apenas consultas SQL diretas em pipelines ETL.
